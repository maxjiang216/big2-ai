# 2026-08-08 — A four-way audit, and a rules bug under everything

Branch: `audit-2026-08`, off `main` at `cbfb047` (PR #40, series-aware net + opp-1-card solver).

The session was an audit first and a fix second: find out what is wrong and what is still
alive before touching anything, because the first finding changes what every strength
measurement in the repo means. One fix landed — the rules bug. Everything else is in
`worklog/TODO.md`.

Four read-only auditors ran in parallel over `web/`, `nn/`, the C++ core and search, and
repo-wide reachability. The findings below are marked **verified** where I reproduced them
myself with a probe or a direct read, and **reported** where they come from an auditor and
I have not independently confirmed them.

## TL;DR

- **`compute_legal_moves` compared a face rank against a bit index for bombs.** Bombs of
  Q and K were treated as unbeatable. This is the authoritative rules implementation, so it
  is under every trained checkpoint. **Verified with a compiled probe, and fixed.**
- **The fix is one line, and the test that guards it also proves the beat relation is now
  globally consistent** — 20 000 random positions, `compute_legal_moves` against
  `get_beating_moves`, zero disagreements.
- **The web app is not affected** — it reads a different, correct beat table. Which means
  the browser plays by correct rules using a net trained under wrong ones.
- **`test/test_legal_moves.cpp` contains zero occurrences of "bomb".** That hole is why
  the above survived.
- **The `--series-v` importance weighting is a no-op** — 100.00% of weights come out
  exactly 1.0. The paused boundary-sampling experiment measured nothing.
- **The deployed net's series inputs are zero-weight**, and cannot train out of it, because
  zero input × zero weight = zero gradient.
- **Five of 39 Makefile targets do not build**, two of them on the critical path of the
  active training loops. CI builds one target, so nothing noticed.
- **The UI rejects ace-triple full houses that the engine allows**, which can leave a human
  unable to answer a trick.
- A live-vs-dead map of the repo now exists: roughly 40 files are dead with evidence, and
  `typed_search` — which I had assumed was dead — is not.

## Details

### The bomb comparison — `src/core/util.cpp:263`

```cpp
const int bomb_rank_min = (lc == bc) ? lr : -1;   // lr is a FACE rank (3..14)
for (int b = 0; b < 13; ++b) {
    if (b <= bomb_rank_min) continue;             // b is a rank INDEX (0..12)
```

Every other branch of this function converts first — `rank_to_idx(lr)` at lines 223, 228,
233 and 238. The bomb branch does not. Since `lr > rank_to_idx(lr)` for every legal bomb
rank, the skip set is strictly too large: the bug **only removes legal moves**, and never
admits an illegal one. That matters for how bad it is — the training data is missing
options, not poisoned with impossible ones.

Verified by compiling a probe against `src/core/util.cpp` and `src/core/move.cpp`, holding
bare bombs of 5/9/K/A:

```
opp plays bomb of Q  ->  legal bomb responses: NONE      (should be: K, A)
opp plays bomb of 4  ->  legal bomb responses: 9 K A     (should be: 5, 9, K, A)
```

Because `lr >= 12` skips all 13 indices, **any bomb of Q or K is unanswerable**. The ace
bomb (rank 14) is genuinely unbeatable, so that case is accidentally correct — which is
part of why this reads as plausible behaviour from the outside.

The second-order effect is the expensive one. `src/players/az_search/az_search.cpp:55`
decides a pass is *forced* when `compute_legal_moves` returns only `kPASS`. A position
whose only legal reply is a higher bomb now collapses into a fused forced-pass node: the
search hands over the trick, and the net is trained on a position the rules cannot produce.
Meanwhile `compute_possible_moves` (`util.cpp:461`) gets ranks right, so the legal-move
generator and the belief model **actively disagree** about whether the opponent can bomb
back.

**Why the web app is fine.** `web/engine.js` never computes bomb legality. It reads a
precomputed `beating[]` list from `az_moves.json`, generated by `get_beating_moves()`
(`util.cpp:305`), which compares `m2.rank > m.rank` — face rank against face rank, no
index anywhere. Verified against the shipped JSON:

```
bomb of Q (rank 12) beaten by bare bombs of rank: [13, 14]   ok
bomb of 4 (rank  4) beaten by bare bombs of rank: [5..14]    ok
ace bomb  (rank 14) beaten by: []                            ok
```

So the fix is one line and needs no asset regeneration and no redeploy. But it also means
the shipped browser game and the net inside it were built against different rules.

**The test hole.** `test/test_legal_moves.cpp` has a brute-force reference implementation
and zero occurrences of the string "bomb" (grep-confirmed). The reference never plays one,
so it could never disagree. The broader lesson is that a reference test only covers the
move classes it actually generates — the suite was not weak, it was *narrow*, and narrow in
a way nothing in it could reveal.

**The fix, and what the test turned up.** One line: `lr` → `rank_to_idx(lr)`. Written
test-first, and the test was watched failing before the fix went in —
`bomb response mismatch after bomb of rank 4: got {9,13,14,} want {5,9,13,14,}`.

Two tests landed. The explicit one walks five bomb ranks including the Q and K cases and
the ace bomb (which must have *no* answer). The second is the more valuable: for 20 000
random positions it asserts `compute_legal_moves` returns exactly
`{m ∈ get_beating_moves()[last] : affordable from hand}`. That pins two independent
encodings of the beat relation against each other — the one the browser consumes via
`az_moves.json`, and the one the search consumes — which nothing previously did.

It passes. So beyond fixing the bomb case, this establishes that the two encodings now
agree **everywhere**, not just where we looked. That was worth more than the fix: it closes
the whole class rather than the instance.

An irony worth recording. Lines 214-217 of the same function carry a comment headed
`Bug fix:` explaining precisely this face-rank-vs-rank-index conversion and why it is
needed. The conversion was then applied to singles, doubles, triples and full houses — and
not to bombs, eight lines below the comment describing it. A previous fix stopped one
branch short.

### The series work is inert in two independent ways

`models/az_seq.pt` is the deployed champion — verified bit-identical to `web/model.onnx`
by comparing `size_embed.weight` across all eleven `az_seq*` checkpoints. That weight is
`(16, 5)` and **columns 3 and 4 — `mpts` and `opts` — are exactly zero**:

```
col0 absmax=2.29   col1 absmax=1.05   col2 absmax=1.44
col3 absmax=0.00  allzero=True    <- mpts
col4 absmax=0.00  allzero=True    <- opts
```

The checkpoint was trained with three side inputs and widened to five by zero-fill at
conversion. `web/worker.js:51` faithfully feeds real running points into those slots and
they are multiplied by zero — the nn auditor confirmed this end-to-end by showing the ONNX
`value` output is **bit-identical** (Δ = 0.0) for `sides=[…,0,0]` versus `[…,0.98,0.02]`.

The part I had not worked out before: these columns can never recover on their own. The
gradient with respect to a weight is proportional to its input, and to the input it is
proportional to the weight — zero-fill is a fixed point. Any fix has to **re-initialise
those columns with noise** before warm-starting, not simply train longer.

Separately, and independently, the reweighting meant to exercise series boundaries never
ran. `nn/dataset_seq.py:300-302` computes `w = natural[a,b] / emp` — a *rate* divided by a
*raw count* — then clips to `[0.1, 10]` **before** normalising to mean 1. On
`data/az_games_gen5.parquet` the raw weights land in `[7.4e-5, 7.3e-3]`, entirely below the
floor, so after clipping and normalising **every weight is exactly 1.0**. Every
`run_az_training_loop.sh --series` run and every `train_az_ii --series-v` trained unweighted
while logging that it had reweighted.

So the paused boundary-sampling round had two unrelated reasons to produce nothing, and the
one recorded in memory — the zero-filled columns — was only half of it.

### The build is broken where the pipeline runs

Five of 39 Makefile targets fail at HEAD. Two of them, `az_selfplay` and
`eval_az_pi_match`, are on the critical path of `run_az_training_loop.sh` and both `az_pi`
loops — neither loop runs end-to-end from a clean `build/`.

One root cause explains four of the five: `player_factory_registry.h` gained `az_ii` and
`az_pimc` factories under `BIG2_WITH_TORCH` on 2026-06-17, and four object lists were never
updated (`Makefile:484`, `:545`, `:642`, `:725`). Only `eval_az_match` and `eval_az_series`
got the full `$(AZ_II_OBJS) $(AZ_PIMC_OBJS) $(AZ_PI_OBJS)` set. The fifth,
`generate_nn_data`, is genuine source rot: it reads `t.hand_at` / `t.opp_at`, which
`nn_game_runner.h` renamed to `hand_after` back in May.

CI did not notice because **CI builds exactly one of 39 targets** (`test_core`). It also
never runs the Python suite (`nn/test_model_seq.py` exists and guards the shipping net's
forward path), never runs the JS suites, and never checks that the three committed derived
artifacts — `az_moves.json`, `az_compose.json`, `az_token_cards.json` — still match their
generators. The last of those is the cheapest high-value check available: no Torch, no
Arrow, and it guards the exact C++/browser boundary that this session found a bug on the
other side of.

### The UI rejects a legal move — `web/cardgame.js:162`

`checkFullHouse` guards with `sorted[2].number !== 1`, rejecting `AAA+xx`. `RULES.md:60`
and `:136` explicitly permit an ace triple in a full house — the rulebook even explains
*why*, since `AAAxx` is only beatable by a bomb while the ace bomb followed by a loose pair
is not. `az_moves.json` contains eleven such moves (ids 158-168). A sweep of all 467
non-pass table moves through `playType` found these eleven are the **only** engine moves the
UI rejects.

The failure is worse than "you cannot play it": when the CPU plays one, `playType` returns
`[-1,-1,-1]`, `state.currType` goes garbage, and `validPlay` rejects every legal higher full
house — so the human can only bomb or pass for the rest of the trick.

Two more live web defects, both reported and one verified by the auditor against the
shipped model: `web/worker.js:43` has no `seq_cap` guard and the ONNX graph **hard-throws
at T ≥ 66** (T=65 passes, T=66 throws), which a long hand plus a deep MCTS path can reach;
and `web/ai.js:41` polls a `ready` flag with no error path and no `worker.onerror`, so a
blocked CDN leaves the loading bar at 40% forever with nothing logged.

### What is actually alive

A reachability pass over the whole repo produced a live-vs-dead map with evidence. The
useful corrections to what I assumed going in:

- **`src/players/typed_search/*` is LIVE.** I briefed the auditor that it was suspected
  dead because `web/README.md:80-82` retires the WASM path. It is linked into `TEST_OBJS`
  (`Makefile:166`), covered by `test/test_typed_search.cpp` in CI, and the registry name
  `typed_search` is the **gen0 teacher** at `src/datagen/az_selfplay.cpp:574`. Only the
  WASM half is dead — `src/wasm/bridge.cpp` and `scripts/build_wasm.sh`, zero references.
- **`nn/train_az.py` is dead as a CLI and live as a library.** `_device`, `_make_optim`,
  `_make_sched`, `_save_scripted` and `masked_log_softmax` are imported by all three newer
  trainers. Deleting it because its own entry point is unused would break the pipeline.
- Confirmed dead with evidence: the whole legacy `nn` line (`nn/model.py`, `nn/train.py`,
  `nn/benchmark_inference.py`, `scripts/run_training_loop.sh` and its four binaries,
  `src/simulation/nn_game_runner.*`), all three files in `tools/` (no Makefile target at
  all; `eval_inspect.cpp` no longer compiles — `forced_search_value` drifted), 13 of 24
  `scripts/configs/*.json`, and roughly 15 analysis scripts.

`web/az_moves.json` was verified byte-identical to fresh `bin/az_moves_gen` output, so the
C++ → browser table has not drifted. Tracked repo size is healthy; the largest blob is
`web/model.onnx` at 5.3 MB, which is intentional.

the six design docs in that directory pre-date the rewrite.

### Housekeeping found on the way

- `.gitignore:126` and `:133` use trailing comments on negation patterns
  (`!assets/*.png  # Keep assets folder images`). gitignore has no inline comment syntax,
  so the comment text is part of the pattern and **the negations never fire** — verified
  with `git check-ignore -v`. `assets/big2-ai-cards.png` is tracked only because it was
  added before the rule.
- `projects/standard-linter/` is an **unregistered git submodule**: it has a `.git` file
  pointing at `gitdir: ../../.git/modules/…` and there is no `.gitmodules`. An unrelated
  project is squatting in the tree, and `black --check .` would lint it if it were ever
  committed.
- `models/` (199 MB) is ignored only incidentally via `*.pt`; the directory has no rule of
  its own, so a future `.onnx` or `.json` there would be committed silently. `logs/` and
  `samples/` are not ignored at all.
